# 検証記録

2026-11-06、日本時間。0.2.0をWindows、Python 3.10.10、uv 0.5.5で確認しました。

## 自動検証

- `uv sync --locked`で検証用仮想環境を作成。8000番で旧サーバーが稼働しているため、その実行ファイルを置き換えず別環境を使用。
- `uv run --locked pytest`相当で**143件成功**。依存先Starletteがhttpxの将来の非推奨化に関する警告を1件出しますが、テストの失敗はありません。
- `ruff check`、`ruff format --check`、`git diff --check`成功。
- `uv build`でsdistとwheelを作成。配布物に`.env`、認証情報、状態DB、仮想環境が含まれないことを確認。
- 別の仮想環境にロック済み依存とwheelをインストールし、配布パッケージからのimport、API構築を確認。

テストは、原文の空白・改行保持、入力装飾の除去、不可視ヘッダー付き投稿と履歴照合、全9感情、フッター欠落・未知コード・破損・重複・引用・本文内の不可視文字保持、補助推論・通知の拒否、SSEとJSON、ACTマーカー、認証、CORS、期限切れ、同時要求、再起動後の保留・照合・解除を扱います。

旧DBの移行前バックアップ、全旧保留状態の自動再投稿禁止、旧完了キャッシュの非再解釈、期限切れの旧識別子の保持、新方式のキャッシュ再生、contentとdisplay_textが異なるケースも確認しています。

別プロセスのUvicornへ実HTTPで接続するテストでは、途中切断後に同一リクエストを再送しても、テスト用Museバックエンドへの投稿が1回だけになることを確認しました。

## 実際のMuseへの読み取り接続

0.2.0の環境から既存の認証で履歴を読み取り、接続の成功を確認しました。この診断による投稿・muse-cli設定変更はありません。

ユーザーがMuse UIで行った不可視文字の往復テストも履歴から再確認しました。userの48文字はUTF-8の「ねこ」、assistantの72文字は「めいど」に復号でき、`payload.content`・`payload.display_text`・トップレベル`display_text`が一致していました。これは2文字種の保持と復号の実証です。新しいAIRI1/AE1規約自体の成功率を実証したものではありません。

0.1.0作成時には製品版CLIのローカルHTTP起動、モデル一覧、ローカル接続検証を確認しました。その際、一度Muse側がWebSocket接続を拒否し、元からインストールされているmuse-cliでも同じ失敗が発生しました。ラッパーはこの状態を`503 / muse_unavailable`として返しました。実接続可否は外部状態に依存するため、利用時に`doctor`で再確認してください。
